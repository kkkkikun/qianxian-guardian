# v0.10.0 WP4 · 主动回合（2026-10-12）——agent 从「被召唤」到「到点醒来干活」

> 规划 WP4 落地：T-24h 到点由守护进程**主动发起决策回合**（天气复核 → ≥60% 降水才
> 起草改期提案写进 app jail；人拍板后走既有白名单链）。与已上报的 RFC octos#2768
> 「宿主应支持 agent 按时间/事件自驱唤醒」构成「提案 + 参考实现」闭环。

## 一、组件与契约

- **守护进程** `tools/qx-proactive-butler.py`：T-24h（days_to==1）且 Confirmed 才决策；
  每 case 幂等标记（qx-proactive-sent.json）。决策分级：
  - 室内/未抽取到地点 → weather_ok 沉默留痕（跳过）；
  - 查不到天气 → weather_unknown 沉默留痕（不发起）；
  - <60% → weather_ok 沉默留痕（不打扰）；
  - **≥60% → 主动发起回合**：候选时段由确定性 pick（顺延同时段）给出，模型只组装
    PLAN 不发明值；回合输出须含 `PLAN{...}` 才写 `pending_plan.json`（无则
    proactive_fail 留痕）。可选 `--room` 发群消息提示。
- **模型通路两档**：`--mode direct`（直连 Kimi API，进程内语义，最稳）/
  `--mode kernel`（octos serve --stdio JSON-RPC，真内核原生 moonshot-coding family——
  RFC 闭环证据；session/open + turn/start + assistant_delta 流）。
- **app 侧**（bundle/main.splash，3 处）：`load_pending_plan()`（enter_chat 读入 →
  复用 plan_parse 全量校验+diff 构建）+ 主动预警 sys 气泡（降水%与 open-meteo 来源）；
  `butler_approve` 成功后 `fs.remove(pending_plan.json)`；`decline_finish` 放弃亦清除
  （一次性提案，放弃=不采纳）。

   - #1 骑车·深圳湾（geocoding 查无坐标）→ `weather_unknown` 留痕「地点未匹配到坐标，
     不发起主动回合」；

2. **守护进程·kernel 模式**（真实 octos 内核 × moonshot-coding/kimi-for-coding）：
   session 已开；本轮直连天气网络失败 → weather_unknown 留痕（与 direct 同语义，

3. **app 提案卡接入**（注入 pending_plan.json，形状与守护进程真实输出一致）：

   拍板 → cases.json 落盘 周二-上午 + pending_plan.json 清除。**PENDING-PLAN-RENDER PASS +

4. **回归**：**27/27**（+R-26 主动提案接入 / R-27 拍板消费）渲染错误 0；

## 三、与 RFC octos#2768 的关系（提案 → 参考实现）

RFC 主张「宿主支持 agent 按时间/事件自驱唤醒」。app 宿主不能自醒是平台事实
（makepad timer 随 isolate 销毁、无宿主 cron）——本 WP4 是场外进程形态的参考实现：
决策环（T-24h 到点→天气复核→≥60% 才动作）、机器提案入 jail、人拍板白名单执行，
全程与 RFC 的「宿主注入 event 触发 turn」语义等价（触发源由进程代替宿主）。
kernel 模式进一步证明：真实 octos 内核原生 family（moonshot-coding）承载该回合。

## 四、诚实边界

- 真实 ≥60% 天气本机不可控（当前实测 53%）——提案路径由注入验证（形状与守护进程
  输出一致），真实天气的两条「不发起」路径全部真实验证；
- 主动回合只覆盖 reschedule（最高价值场景）；complete/cancel 等其它提案类型未扩；
- `--room` 群消息提示本轮未连 palpo 验证（palpo 栈可用，链路复用 bridge 已证通路）。
