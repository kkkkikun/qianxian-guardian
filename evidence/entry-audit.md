# 入口闭环审查（#26）

> 任务：功能完整性审查（只读不改）
> 范围：`app/qianxian/bundle/main.splash` 的 13 个 UI 入口 handler
> 三问：①成功路径有反馈吗 ②异常/前置缺失时是否明确告知用户缺什么 ③状态是否自洽

---

## 0. 评估口径

- **反馈**：是否调用 `ui.hint.set_text(...)` 给用户文字说明（成功 / 失败 / 阻塞三种语义）
- **前置缺失**：必填参数（id 选中、输入框非空、文件存在、capability 可用）检查
- **状态自洽**：操作后 in-memory + cases.json + 扁平数组 三者是否一致
- **判定**：
  - ✅ 闭环良好
  - ⚠️ 反馈存在但有小问题（建议改 / 可不改）
  - ❌ 无反馈或状态不自洽（建议改）

## 2. 具体问题定位 + 最小改法 + 是否值得改

### 2.1 确认守护的「fallback」语义 ⚠️

**位置**：`confirm_case` 行 873–903（特别是 882–883、894–895、899）

**问题**：未选中时 `target_id()` 退到最新一条；成功 hint 带 `tag = "（作用于最新一条，因未选中）"`，但**已 Confirmed 早返分支（行 883）和 fail 分支（行 897）也带 tag**——这条 tag 只在 fallback=true 时显示，逻辑是对的。**唯一小问题**：行 883 早返时 `tag` 计算了但用户看不到 #N 状态外的进度反馈（已是 Confirmed 再按无副作用，符合预期）。

**最小改法**：无需改（行为正确）。

**是否值得改**：❌ 不改。

---

### 2.2 重新收敛后回执快照的可见性 ⚠️

**位置**：`reschedule_case` 行 921–928

**问题**：行 921 把 status 改回 Proposing，行 924–927 清空 receipt_activity/place/text/done 四个字段。`rebuild_lines()` 内 Confirmed 分支才会填回 receipt（行 1583 附近），所以 Proposing 状态下 receipt_* 字段确实是空——逻辑正确。**但**：用户刚"改口"，看到的卡片 receipt 区从「已填满4行」变成「4行空白」会显得突兀，且 hint 只说"重新收敛（旧确认作废）"未提及 receipt 被清空。

**最小改法**：行 936 hint 文案追加 "（回执快照已清，下次确认时重填）"。

**是否值得改**：⚠️ 改了体验更顺，不改也能跑（字段语义正确）。成本 1 行文字，**值得改但优先级低**。

---

### 2.3 改时间的默认初值静默写入 ❌

**位置**：`cycle_slot` 行 531–539

```splash
let sd = "" + cases[cur]["slot_day"]
let sp = "" + cases[cur]["slot_part"]
let nd = "周六"
let np = "上午"
if sd == "周六" && sp == "上午" { nd = "周六"  np = "下午" }
...
// 5 个 if 都不命中 → nd/np 仍是 "周六/上午"
```

**问题**：当 `cases[cur].slot_day = ""`（没抽到）或抽到非 5 槽之一（例如「周三」）时，5 个 if 全不命中，`nd/np` 仍是默认的"周六/上午"。结果：**用户点"改时间"按钮，slot 从未知 → 周六上午**，但 hint 行 597 只说"已改时间 → 周六上午"——用户看不出来自己被从"未知"重置成了"周六上午"。状态不自洽：原状态本来是"没时间"，现在变成"周六上午"。

**最小改法**：行 539 之后追加：
```splash
if !(sd == "周六" || sd == "周日") || !(sp == "上午" || sp == "下午" || sp == "晚上") {
    ui.hint.set_text("原时间未抽取到常见槽位，已重置为 周六上午（#" + id_str + "）")
    // 仍写入新值，但 hint 明示用户「这是重置」
} else {
    ui.hint.set_text("已改时间 → " + nd + np + "（#" + id_str + "）")
    ...
}
```

**是否值得改**：✅ **值得改**。当前是**静默覆盖**，违反"状态不自洽"红线；改法是显式告知用户「被重置」，而不是猜。

---

### 2.4 导出数据的屏显溢出 ⚠️

**位置**：`export_data` 行 1153–1155

```splash
ui.hint.set_text("—— cases.json 原文（复制可备份）——\n" + raw + "\n—— 复制以上文本即可备份 ——")
```

**问题**：hint 区是单行 Label，长 JSON 塞进去会撑高整个屏幕。30 条以上 case 时屏显基本无法阅读。

**最小改法**：要么把导出拆到独立只读 TextArea（API 是否支持需查 SCRIPT-API.md，本审查未查），要么在 hint 文案末尾追加"（N 字符，过长请用 AI 解析/导出工具）"做长度警示。

**是否值得改**：⚠️ **不划算**。本 runtime 受限（PRIVACY.md 承诺不出网、无系统分享 API），大 JSON 屏显是这个环境下的「最佳替代方案」。改独立 TextArea 涉及 UI 结构改动，风险大于收益。

---

### 2.5 清空全部的 remove 失败判定 ⚠️

**位置**：`clear_all_data` 行 1178–1183

```splash
if fs.exists("cases.json") {
    let rr = fs.remove("cases.json")
    if rr != nil {
        removed_msg = "" + rr
    }
}
```

**问题**：`fs.remove` 失败时返回值经 `"" + rr` 转字符串可能为空（错误对象被序列化为空），导致 `removed_msg == ""` 走到 1213 行 "已清空 N 条（cases.json 已移除）" 分支——但**文件其实没删**，用户以为清理干净实际磁盘残留。

**最小改法**：行 1180 加额外检查：`if rr != nil && "" + rr != ""`；或统一用 #13 的 `save_result = if r == nil { "ok" } else { "fail" }` 模式（与 `save()` 行 399–407 一致）。

**是否值得改**：✅ **值得改**。这是数据丢失类风险，外环复验 #13 已规定字符串标记判成败的范式，本处未严格沿用——一致性应当对齐。

---

### 2.6 AI 解析回调无超时 ⚠️

**位置**：`ai_parse` 行 1105–1108

```splash
host.request("octos.turn.start", {...}, fn(r){
    if r.is_ok { ... } else { ... }
})
```

**问题**：`host.request` 回调若不触发（网络挂起、service 静默超时），用户会卡在 "AI 解析中…" 永远不变。**无超时兜底**。

**最小改法**：行 1104 之后启动 `start_timeout(15.0, || { ui.hint.set_text("AI 解析超时（15s），已降级为本地规则") })`；回调触发时由闭包内某 flag 阻止超时覆盖。但这会引入 flag 管理成本，与现有 5s 撤销窗口模式冲突。

**是否值得改**：❌ **不划算**。AI 解析是「可选增强」，本应用的核心承诺是「无 AI 完整可用」（注释行 2–3）。15s 后用户自行重试或用本地规则都是合理路径，加超时反而引入状态复杂度。
