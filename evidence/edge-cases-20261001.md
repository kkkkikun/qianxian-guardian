# 边界与安全测试记录（2026-10-01，#19 之后）

> 目标：验证真实用户最容易触发的边界——超长文本、特殊字符/注入串、重复创建、存储增长。
> 环境：自建 card-host（App-Hub `46d67e5` + makepad `db4691d0` + OSM `3d3ef80`），headless `/snap` + jail 自证。

## 1. 超长文本

| 输入 | 结果 |
|---|---|
| 重复 60 次「周六上午」（约 240 字，无约定语气） | 不崩、不误建、无 splash 错误 |
| **真实长消息 228 字**：「周六上午我们一行五人约在深圳湾公园北门集合骑车，顺路去海岸城吃饭，人均预算两百，迟到的人自己打车，结束后下午三点各回各家，记得带上雨伞因为天气预报说有雨」 | ✅ 自动建；`activity=骑车`、`place=深圳湾`、`slot=周六-上午` **全部正确抽取**；文件仅 461 字节 |

结论：长文本不触发截断/崩溃，抽取在长文本上依然准确。

## 2. 特殊字符与注入串

输入：`周六上午去深圳湾骑车 <script>alert(1)</script> "引号" '反斜杠' 100% $100 & 特殊 #标签 @mention`

结果：
- ✅ 正常建守护，`activity=骑车`、`place=深圳湾`、slot 正确
- ✅ **`<script>` 仅作为纯文本存储与显示，无任何执行**（本 runtime 的 Label 只渲染文本）
- ✅ 引号 / 反斜杠 / `%` / `$` / `&` / `#` / `@` 全部原样保留在 `cases.json`
- ✅ 无 splash 错误

> 说明：这是"应用层不做注入"的**表现**——真正的防线是架构性的：应用无网络
> （`hosts: {}`）、无 eval、无外部脚本加载。文本被原样存储这一事实本身也说明
> **我们不做字符串拼接式的信任假设**（`to_json()` 整体序列化，不手工拼 JSON）。

## 3. 重复创建与存储增长

连续点 6 次「用示例试试 + 建守护」：

| 指标 | 值 |
|---|---|
| 守护条数 | 6 |
| `seq` | 6（自增正确，无 id 冲突） |
| `cases.json` 大小 | 1615 字节 |
| 计数显示 | `共 6 / 6 条` |
| splash 错误 | 0 |

对照 `fs` 限制（单文件 1 MiB / jail 16 MiB）：按每条约 270 字节估算，
**约 3800 条才会触及单文件上限**，远超初赛/复赛的使用规模。

## 4. 已知边界（非缺陷）

- **时间槽只判「同一天同一时段」**：本 runtime 无时钟/日期 API，不做精确时刻比较，
  已在演示脚本与 `ux-specs` 中如实说明。
- **分诊是关键词规则**：命中时间词且命中活动/约定语气才自动建；只有时间词走澄清卡
  并给「仍然建守护」入口（不拦死用户）。收紧了误报，也必然存在漏召——
  这是**确定性规则**的固有取舍，AI 增强入口正是为此保留。

## 5. 结论

四类边界（长文本 / 特殊字符 / 重复创建 / 存储增长）全部**不崩溃、不丢数据、
不误判严重**，与 `ux-specs.md` 记档的平台限制一致。
