# 与官方「日历」场景的对齐（2026-10-01）

> 依据：`OctoSense 官方 12 场景指南 · 日历`
> （本地留存 `../research/octosense官网-12场景指南全文.txt`）。
> 官方场景原话：「会议改到更早的时间和另一间办公室，**新的时段恰好与私人预约冲突**」，
> 四步演示为：① 打开变更邀请 → ② 看见安排重叠 → ③ 审阅改期提案 → ④ 明确什么尚未确认。

## 逐条对齐

| 官方场景步骤 | 牵线的实现 | 证据 |
|---|---|---|
| ① 打开变更邀请，检查新时间是否冲突 | 新建守护时抽取时间槽（周六-上午），与已有非取消守护比较，命中即标 `conflict` | `cycle_slot()` 同款比较逻辑；`/snap` 实测「待拍板·冲突」 |
| ② **看见安排重叠**，说明冲突原因，**保留现有安排供判断**，建议改到别的时段 | 折叠态直接显示「⚠ 时间冲突：…也占「周六-上午」时段」；**不自动取消任何一方**；底部「改时间（5 槽）」可改到 14:30 式的另一时段，改完自动重算 | 真机：改时间后冲突自动解除（`conflict: yes → no`） |
| ③ 审阅改期提案（明确列出会议、组织者、拟议时间） | 展开态逐项列出：状态 / 时间 / 参与人 / 活动 / 地点 / 原文 / 回执四行 | 真机：展开态 7 段全部渲染 |
| ④ **明确什么尚未确认**（建议 ≠ 已改期，等待组织者回应，私人预约仍保留） | 状态机三态分离：`Proposing`（待拍板）/ `Confirmed`（组织者已确认）/ `Cancelled`；改口回 `Proposing` 且回执刷新；未确认前不生成对外动作 | 真机：确认链 `Proposing → Confirmed`；改口回 `Proposing` 且回执重生成 |

## 官方场景的核心动词 ↔ 我们的实现

官方日历场景写明三个核心动词：**时间收敛、冲突检测、待定 vs 已确认**（`task.md` 开篇即引用）。

| 官方动词 | 牵线 | 性质 |
|---|---|---|
| 时间收敛 | 从群消息抽星期 + 时段 → `周六-上午`（抽不到就留空，**不编造**） | 确定性规则，无 AI 也可用 |
| 冲突检测 | 同一天同一时段与已有安排比对，双向标记 | 确定性规则（无时钟 API，不做精确时刻比较，已如实说明） |
| 待定 vs 已确认 | `Proposing` / `Confirmed` 两态 + 组织者确认动作 | 状态机，**冲突只提示不自作主张** |

## 诚实边界

- 本 runtime **无时钟/日期 API**，因此只判「同一天同一时段」，不做「9/29 与 9/30」这类精确比较；
  官方场景里的「14:00 → 13:00」我们用 5 个常见时段轮换近似（周六-上午/下午/晚上、周日-上午/下午）。
- 无提醒推送能力（`T-24h 提醒` 以**本地提醒文本占位**呈现，明示需宿主定时能力）。
