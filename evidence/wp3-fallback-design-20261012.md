# WP3 · 群智收敛——降级路径设计（先行，主路径前置条件）

> 约束 5：先做降级路径设计，再动主路径。本文是 WP3 的降级蓝本——当 Rinx 的
> `m.replace`（活卡片原地更新）或「成员独立授权投票」接口事实不达标时，WP3 以本
> 形态交付，UI 明示降级；主路径达标时本形态作为「宿主不支持时的诚实兜底」保留。

## 一、降级形态：文字投票卡 + 手动刷新

**目标不变**：从「组织者单人工具」跃迁为「群体协调协议」——守护卡进群，成员表态，
管家收敛出 PLAN。降级路径用**纯文本消息**承载同一协议，不依赖任何卡片渲染/编辑能力。

### 协议（确定性，零 AI 参与计票）

```
① 组织者：详情页点「发投票到群」→ app 经 matrix.send_message 真发一条文字投票卡：
   「📋 时间收敛投票：#2 骑车 · 深圳湾
     候选时段（回复对应字母即投票）：
       A. 周六-上午    B. 周六-下午    C. 周六-晚上
       D. 周日-上午    E. 周日-下午
     回复如「A」或「AB」（多选按 Telegram Multiple Answers 语义）。
     截止：组织者说「收敛」时锁票。当前已收到 0/0 票（成员回复后请组织者点「刷新计票」）。」

② 成员：在群里回复字母（A-E）——**各自的 Matrix 账号天然独立授权**（消息 sender 即身份）。
   一人一票：重复回复以**最新一条**为准（改票幂等）；多选按集合计。

③ 组织者：app 内点「刷新计票」→ 守护进程/ app 读房间消息（matrix.read_messages），
   按 sender 去重+最新票归票 → 确定性计数（A:2 B:3 C:1 D:0 E:1）显示在 app 内；
   「已报 N/M」（M=参与人名单数）确定性呈现，零 AI。

④ 收敛：组织者点「管家收敛」→ agent 读计票分布出 PLAN（reschedule 到票数最高时段，
   解释只引用计票数字）；「考虑过但票数不足的时段」进沉默留痕（suppressed.json kind=converge）。
   人拍板 → 白名单 reschedule 落盘 → 回执进群（「定档：周日-下午，3/7 票」）。
```

### 越权与失败态（与主路径同语义）

- **非成员投票**：不在参与人名单的 sender 票数不计（提示「非成员表态不纳入」）；
- **改票**：同 sender 多票取最新（幂等）；
- **零票/平票**：收敛时如实显示「票数不足/平票，请人工定夺」，不编造最优；
- **matrix 无服务**：app 诚实降级为「本机生成投票文案，手动复制转发」（屏显可复制）。

## 二、与主路径的关系（同一协议，两种承载）

| 维度 | 主路径（若接口达标） | 降级路径（本设计） |
|---|---|---|
| 承载 | 群内卡片 m.replace 原地更新 | 纯文本消息 + app 内「刷新计票」 |
| 投票交互 | 成员打开小程序独立授权点选 | 成员回复字母（Matrix sender=身份） |
| 计票 | 实时（卡片原地刷新） | 手动刷新（读房间消息归票） |
| 防刷屏 | m.replace 原地更新 | 只发一条投票卡，计票在 app 内显示 |
| 收敛 | 管家读分布出 PLAN（同款） | 管家读分布出 PLAN（同款） |

**收敛语义、PLAN 生成、拍板白名单链、沉默留痕、回执进群——主/降级完全一致。**
差异只在「成员怎么投票」与「进度怎么呈现」。

## 三、UI 明示降级

- 详情页「发投票到群」按钮旁常驻一行小字：「群投票：文字卡形态（本宿主不支持活卡片原地更新）——协议一致，计票手动刷新」；
- 主路径达标后该行撤下，换「群投票：活卡片（原地更新）」。

## 四、本设计的可复用件（无论主路径是否达标都交付）

1. `tools/qx-converge.py`：房间消息读取 + 字母票归票 + 确定性计数（幂等/非成员拒收/最新票覆盖）——独立可测；
2. app 内「发投票到群 / 刷新计票 / 管家收敛」三按钮链路（白名单 PLAN reschedule 收敛）；
3. 计票单测：重复投票/非成员/平票/零票四类否定用例。
